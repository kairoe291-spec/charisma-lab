## 已有工作与边界解释

- 开始时工作区已有未提交的 P1 实现及新设计文档，全部保留；package.json 仍为 2.0.0-p1，本轮不重新定义版本号。
- Feature 内保存业务 UI、状态和本功能计算/用例；根 services 仅放实际跨功能复用的保存生命周期协调器。该协调器不是持久化 Outbox，不产生第二套业务 Service。
- shared 只包含通用 UI；原有云账户、游客迁移和冲突组件留在 components，本轮不迁移云功能。
- types 集中已有内容类型和领域 payload 别名；持久化契约 src/domain/types.ts 保持原样，以免触碰数据与同步层。旧路径保留必要的兼容导出，只有一份实际实现。
- 文档中 IndexedDB → Supabase“切换”的歧义留待后续 ADR 澄清。本轮继续保持本地 Repository 为写入入口。
- 数据库蓝图与现有通用 records 模型的差异不在本轮解决。数据库名称、version(1)、Store、索引、ownerScope、ID、备份格式和原子事务保持原样。

### 当前边界

- Page：页面入口和 Feature 组合；Dashboard 接收原有 profile/percent。路由、URL、查询参数与布局保持。
- Feature：本业务 UI、状态、查询与用例。局部 Service 使用原有 Repository，不重新定义数据访问层。业务规则与评分语义保持。
- Shared：通用展示组件、Dialog、Toast/反馈，不依赖业务模块或数据库。
- Data：原有 Repository、Dexie 与持久化事务；本轮文件内容保持。
- Services：只有原保存生命周期协调器。与 Feature Service 职责不同，与持久化 Sync Queue 无关。
- Types：已有内容类型与领域 payload 类型别名；domain/types 继续作为持久化契约。类型集中不构成 Schema 迁移。

ESLint 对八个已迁移页面、Features 和 Shared 加入导入边界限制。通过内存中的违规导入样例确认三类限制会报错，没有生成测试占位文件。Settings、App/SyncProvider 和既有 cloud/components 的历史边界留待后续，不伪称全项目已经完成分层。
