# P1 云账户与可靠同步设计

**状态：设计与后续任务，不是已运行的云系统。** P0 已提供本地 Repository、记录归属字段、Outbox 和软删除。P1 需要真实 Supabase 项目、迁移、客户端接入和下列测试通过后才能启用。此文不提供可以直接粘贴到生产库的示意迁移。

## 1. 必须保持的数据安全条件

1. 本地操作先提交 IndexedDB，业务记录与 Outbox 在同一事务中修改。
2. React 页面通过 Repository 访问私人数据，不直接用 Supabase 覆盖本地 CRUD。
3. 本地保存与远程同步分别反馈。只有服务端确认操作、客户端持久化确认后才显示该操作已同步。
4. 云端版本和云端更新时间由服务端生成；设备时间仅展示，不用于冲突裁决。
5. 登录、退出、账号切换不自动清空游客或其他账号数据，不自动上传别人的内容。
6. 日志和笔记发生冲突保留两份；未经用户选择不使用最后写入者获胜。
7. 请求超时、重复提交、服务器错误、部分成功、会话失效均不丢本地记录。

## 2. 身份空间与认证

本地使用独立空间：

```text
guest:<安装实例 UUID>
user:<Supabase user UUID>
```

认证模块暴露活动 scope 与递增的 sessionEpoch。Repository 的每个查询要求明确 scope；不能先取全库再让 UI 隐藏别的用户。退出时切换回 guest scope，清理 React 内存状态、订阅和编辑器草稿；保留旧账号的本地数据供该账号以后使用。

同步请求绑定发起时的账号 ID、scope 和 sessionEpoch。账号切换后旧请求即使返回，也不能写入新的活动空间或改变新账号的状态栏。不同账号数据不得进入同一个上传队列筛选结果。

Supabase 会话恢复与本地数据解锁应明确：已经在当前设备使用过的账号可按产品规则继续离线访问其本地空间；离线无法完成新的云登录。匿名用户不被强制注册。

邮箱登录采用 OTP 或 Magic Link。当前应用 HashRouter 占用 URL fragment，Magic Link 接入需要专门的认证回调处理，并在处理完会话后恢复业务路径；不能把认证 fragment 当普通页面路由。参考 [Supabase 邮箱登录](https://supabase.com/docs/guides/auth/auth-email-passwordless) 和 [回调允许列表](https://supabase.com/docs/guides/auth/redirect-urls)。

## 3. 游客迁移

登录成功后先进入当前用户空间，不把游客记录悄悄并入云端。若游客空间有记录，显示记录数和备份按钮，提供“合并到当前账号”“保留游客数据”“取消迁移”。取消仅取消迁移，身份状态按 UI 明确展示。

迁移采用可恢复的 migrationId 和逐记录映射：

- 原游客数据保留，迁移前导出备份并保存本地安全快照。
- 拷贝生成账号空间记录及 Outbox，创建和迁移进度在同一事务中落库。
- 用 migrationId + 源记录 ID 的稳定映射去重，重试不会重复创建记录。
- 同名 / 相同标题不认为同一条记录；ID 冲突且内容不同应创建副本，不自动覆盖账号数据。
- 上传中断后继续未确认操作；仅凭登录动作不删除原游客记录。
- 明确迁移范围包括哪些 Tombstone，防止把备份中已删除的内容当新记录恢复。

## 4. 云端模型与授权

拟使用 `profiles` 与 `user_records`。`user_records` 至少包含 `id`、`owner_id`、`kind`、`payload`、整数 `version`、服务端 `created_at/updated_at` 和 `deleted_at`。记录主键应明确采用全局 UUID 或 `(owner_id,id)`；客户端和 RPC 使用同一规则。

`kind` 仅允许已定义的私人业务类型；数据库限制 payload 为 JSON object、大小和必要字段类型。Zod 前端校验是体验和兼容性保障，不能替代服务端校验。静态课程、公开案例与题库不写入私人记录表。

私人表开启 RLS，为 SELECT、INSERT、UPDATE、DELETE 分别设置用户归属政策。INSERT 的 `WITH CHECK` 验证 `auth.uid() = owner_id`；UPDATE 同时限制旧行可访问和新行归属，并禁止变更 owner_id。配置必要 GRANT 并限制列 / 函数权限；RLS 与 SQL 权限都需要有效。

浏览器仅使用 publishable key。[Supabase 密钥文档](https://supabase.com/docs/guides/getting-started/api-keys) 与 [RLS 文档](https://supabase.com/docs/guides/database/postgres/row-level-security) 是部署时的检查依据。RLS 不是端到端加密；有管理员权限的人仍可能访问数据库内容。

## 5. 条件写入 RPC 与幂等凭证

不能先在客户端 SELECT 版本，再无条件 UPDATE。两个设备可能同时通过检查。服务端在一个数据库事务内完成身份检查、版本比较、写入和幂等凭证保存。

拟设 `mutation_receipts`，以 `(owner_id, mutation_id)` 唯一；保存规范化请求哈希、结果类型、记录 ID、服务端提交版本及返回结果。RPC 流程：

1. 从 `auth.uid()` 取得 owner；拒绝未认证请求，不信任客户端传入的 owner_id。
2. 验证 entity kind、记录 ID、操作、payload 和 expected/baseVersion。
3. 若该 mutation 已处理，验证请求哈希一致，返回此前结果；同 ID 不同内容拒绝。
4. 对当前记录执行行锁或原子条件写入。创建要求不存在且 baseVersion 为 0；更新 / 删除要求服务端 version 与 baseVersion 相等。
5. 不一致返回冲突及可见的当前版本，不覆盖。
6. 成功时服务端版本加一并设置服务端时间，写入记录 / Tombstone。
7. 保存 receipt，再一起提交。客户端即使丢失响应，重试同一 mutationId 可获得同一成功结果。

并发重复请求必须由唯一约束、事务锁和冲突重查保证只有一次实际写入。RPC 如果使用 SECURITY DEFINER，固定安全 search_path，显式检查 auth.uid，撤销 PUBLIC execute，仅授予必要角色；不能仅靠函数调用者传入的 ID 限制归属。

直接写 `user_records` 的权限与版本管理必须与 RPC 方案一致：若写入只允许 RPC，应撤销 authenticated 的直接 DML 写权限，同时保留需要的读取权限，防止绕过 CAS。分别测试策略和函数权限，不能以“RLS 已开”代替验证。

**receipt 不能按短期限盲目删除。** 很久离线的设备仍可能重试已经成功但未收到响应的操作。第一版保留凭证；后续清理需要设备确认水位、支持期限、幂等归档或能证明安全的协议。

## 6. 本地 Outbox 状态机

每项保留 mutationId、entityType、entityId、ownerScope、operation、payload、baseVersion、createdAt、retryCount、nextRetryAt、状态及错误原因。

```text
pending → sending → acknowledged
            ├─ 可重试错误 → pending（指数退避）
            ├─ 会话失效   → blocked-auth
            └─ 版本不同   → conflict
```

`sending` 在页面关闭后需要恢复成可重试，不能永久卡住。服务端用 mutationId 防重复；多标签页可用 Web Locks 或有到期时间的 IndexedDB lease 协调上传者。即使协调锁失效，服务端幂等性仍必须有效。

提交中的 payload 必须冻结。若用户在上传过程中继续编辑，新增后继操作；不能复用同一个 mutationId 改写已发送 payload。一个实体按顺序发送，前一操作确认后把真实服务端版本作为后一操作的基础版本。仅在从未发送且确认没有外部执行风险时，才可合并 pending 操作。

确认响应时，用一个 IndexedDB 事务保存远程版本、确认对应 mutation、更新同步元信息。如果期间产生新编辑，只确认旧操作，保留新操作和编辑内容；不能拿旧响应回写覆盖最新本地 payload。数据同步状态从该实体剩余操作推导。

采用有上限的指数退避加抖动；保存 nextRetryAt，重启后继续。登录失效不无限请求，提示重新认证。人工“重新同步”允许提前重试但不生成新的 mutationId。

## 7. 双向同步与完整拉取

触发条件：网络恢复、登录完成、页面重新激活、手动同步；定时仅作补充。每次 run 固定用户身份，不上传 guest scope。

第一版可以完整拉取当前用户记录，包含 Tombstone。分页使用稳定、唯一排序键及 keyset pagination，不能仅用设备时间或非唯一 updated_at 作游标。记录集合拉取与分页期间的新增更新并发需明确一致性方案：使用服务端同步 revision / snapshot 边界，或完整扫描后按 revision 复核直到无遗漏。没有完整扫描成功前不推进“最后成功同步”水位。

处理顺序可为先拉取核对 → 有序上传 → 再完整拉取。远端回包与本地记录版本比较：

- 无本地待变更：事务内应用云端记录或 Tombstone。
- 有待变更、基础版本等于云端：保留本地编辑，按 CAS 上传。
- 有待变更、基础版本不同：保存冲突，不覆盖任何版本。
- 尚未收到 receipt 的超时操作：先重试或查询幂等结果，不能把自己已提交的云版本误判成他人修改。

HTTP 失败或某页失败保留本地队列与原同步状态。不能把缺失于一次不完整响应的本地记录删除。远端明确 Tombstone 才传播删除。

## 8. 冲突处理

ConflictRecord 保存用户空间、记录 ID、本地内容、冻结的本地操作、云端完整版本、两边显示时间、设备信息及状态。长篇日志 / 笔记不自动覆盖。

界面允许保留本地、保留云端、手动合并、创建副本或暂时跳过。选择本地或合并时，使用用户看到的云版本作为新的 baseVersion 再进行 CAS；若云端又变化，应重新展示冲突。选择云端仍需在本地事务中保留原内容的可恢复副本，再按用户确认移除相关待操作。

简单训练记录也不随意按时间合并：不同现实训练用独立 UUID；重复 mutation 依 receipt 去重；对同一记录的状态冲突按明确行为规则处理或交给用户。

## 9. 删除与 Tombstone

本地软删除与删除 Outbox 在同一个事务中保存，界面隐藏；云端 CAS 更新 deleted_at 并增加 version。远端删除与本地离线编辑冲突时先保留本地内容供用户选择，不允许旧设备把 Tombstone 无条件重建成正常记录。

第一版不定期清除 Tombstone。未来清理需要所有已注册设备确认删除版本，或明确退休长期离线设备并强制完整重建同步基线。云端物理删除账号数据是单独的隐私流程，必须身份确认和二次确认，不假借“同步清理”删除私人内容。

## 10. 备份、恢复与云身份

P0 JSON 包含 schemaVersion / appVersion / exportedAt / records。导入校验后进行预览，在当前空间重写 ownerScope；备份内的云版本、身份和同步状态不作为可信授权。

P1 在账号空间导入时应作为新的明确本地操作排队，不将旧备份冒充云已确认状态。合并时保留已有不同内容并创建副本；替换操作要定义云端是否也删除，默认不能悄悄删除服务器记录。云端的“恢复备份”需要单独确认语义和 Tombstone 影响。

## 11. 实施顺序与验收

先实现数据库迁移和服务端授权 / 幂等测试，再接认证与本地空间切换，之后实现上传、完整拉取、冲突 UI 和真实双设备测试。公开配置是接入必要条件，不能代替工程验证。

| 测试 | 必须验证 |
| --- | --- |
| A 本地持久化 | 新建、修改、刷新后内容一致；事务失败时没有孤立 Outbox |
| B 离线 | 缓存后断网创建 / 编辑，关闭重开仍在；重连确认后逐项同步 |
| C 双设备 | A 创建 → B 读取 → B 修改 → A 读取；两端真实账号同一用户 |
| D 冲突保护 | 两设备改同一日志；保留双方版本；选择时再发生远端变化仍能检测 |
| E 身份隔离 | A 退出 B 登录后 UI 无 A 数据；B API 不能 SELECT / INSERT / UPDATE / DELETE A 数据；不能改 owner_id 绕过 |
| F 同步异常 | 超时已提交后重试、并发同 mutation、请求中断、500、会话失效、部分成功、上传时再编辑；无重复且队列可恢复 |
| G 备份 | JSON 导出 / 恢复一致，错误 schema 与重复 ID 全部拒绝；导入失败原数据保留 |
| 多页与并发 | 两标签上传不重复；分页中增加 / 修改记录无遗漏；中途一页失败不推进完整水位 |
| 长期离线设备 | 旧设备提交到已删除记录得到冲突，不复活；receipt 仍能确认旧请求 |
| 游客迁移 | 取消不丢数据；中断重试无重复；迁移原游客数据保留 |

RPC 与 RLS 测试应放入 `supabase/tests/` 并在隔离测试项目执行。假远端适合验证客户端状态机，但不等于真实 RLS、网络、手机或双设备验收。

## 12. 完成 P1 后才允许显示的能力

必须有真实认证、正确 RLS、可靠 CAS / 幂等、完整两向同步、冲突保护、身份隔离和可复现测试，才能展示“云端同步完成”“跨设备恢复”。配置缺失、离线或授权失效时继续本地学习，并明确记录尚未上传。
